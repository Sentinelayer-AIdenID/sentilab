# Open-proposal contract v1 (OP-F1)

The language-neutral contract every client and server of ticket `e76b348f` shares: `sl session reply`, the `sl` MCP
`session_reply`, the hosted MCP `sessions_reply`, plain REST, the check, the intake, the recorder, the judge pages
and the skill. Design: `docs/sentilab/open-proposals/DESIGN.md` (PR #59). Where the provisional challenge contract
(`docs/sentilab/reviews/2026-10-31/challenge-math-1606/PROVISIONAL-CONTRACT.md`) or a later review decision differs
from the design, the decision wins. Every threshold and limit here is **provisional** until frozen.

Nothing here runs a solver, reads a clock or touches the network. The Python reference is
`open_proposals/contract/`; the JavaScript twin of the canonical form and hashes is `canonical.mjs`.

`--check` fails if a committed file differs. Run `node run-vectors.mjs` here and
`python -m unittest open_proposals.contract.test_golden open_proposals.contract.test_rules` from the repo root.

## Canonical form

RFC 8785 (JCS), as `sentilab_core/envelope.py` implements it: object keys sorted by UTF-16 code units; numbers in
ECMAScript shortest round-trip form (`-0` is `0`, `1e21` is `1e+21`); strings escape only `"`, `\` and control
characters; no whitespace; UTF-8. A nonfinite number or a lone surrogate is refused, never written.

Units are in the field names: `_um` integer micrometres, `_mm` millimetres, `_c` degrees Celsius, `_k` kelvin
(differences), `_s` seconds, `_w` watts. Geometry is integers only, and "integer" means a JSON integer literal:
`17000.0` and `1.7e4` are refused as `schema_invalid` (`type`), so every encoder agrees once keys are sorted.

## Hashes and keys

| Name | Value | Who computes it | Public |
|---|---|---|---|
| `manifest_id` | `sha256(JCS(manifest))` | anyone | yes |
| `geometry_sha256` | `sha256(JCS({"schema":"sentilab-open-geometry/1", problem, fixture_config_sha256, units, anchor, lattice_um, dies:[{die,x_um,y_um,rot_deg}]}))`; `fixture_config_sha256` is the manifest's | the client; the server recomputes it | yes, never for a sealed entry |
| `proposal_sha256` | `sha256(JCS(proposal))`, the whole proposal; the status key and, for a sealed proposal (which carries a salt), the retry identity | the client | yes, salted when sealed |
| `body_sha256` | `sha256(note bytes)`, the exact bytes Senti returned | the intake | yes |
| `source_ref` | `sha256("sentilab-open-source/1:" + action_id)` | the intake | yes |
| `participant_ref` | `HMAC-SHA256(challenge key, JCS(["sentilab-open-pseudonym/1", challenge, account_id]))`: a per-challenge keyed pseudonym of Senti's `actorUserId` | the recorder | yes; the account id only in restricted records |
| `transport_id` | `"open-tk1-" + sha256(JCS(["sentilab-open-transport/1", room, account_id, actor_slot, manifest_id, proposal_key, proposal_sha256]))`, 73 characters; `actor_slot` is `human` or `agent:<agentId>` | the client sends it as Senti's `idempotencyKey` | no |
| `run_id` | `open-<manifest_id 8 hex>-<participant_ref 16 hex>`, or `...-sentilab` | the recorder | yes |
| `salt` | 32 bytes as hex: fresh entropy kept for retries, or `HMAC-SHA256(client secret, JCS(["sentilab-open-salt/1", manifest_id, proposal_key]))` | the client | never |
| `capability` | `"opencap1-" + HMAC-SHA256(salt, JCS(["sentilab-open-capability/1", manifest_id, proposal_sha256, epoch]))`, epoch from 1 | the client; the server re-derives it after opening | never; a bearer secret, records keep `capability_sha256` |
| `ciphertext_ref` | `sha256(decoded age file bytes)` | the server, returned to the client | private receipt |

**Two keys.** The logical key is `(account, manifest_id, proposal_key)`. The transport key (`transport_id`) also binds
the room, the actor slot and the canonical content hash, and fits every transport's `Idempotency-Key` (hosted MCP
128, REST 180 visible characters): identical content gives an identical key, changed content a new one.
`decide_revision` (`open_proposals/contract/states.py`) applies the logical key, in submission order:

- The first submission of a logical key owns it for good, whatever its outcome.
- The same key with the same `proposal_sha256` is a duplicate: no new record, the same receipt.
- The same key with other content is a new revision, rejected `revision_conflict`: recorded, never an overwrite.
- A `parent` must be the `geometry_sha256` of one of the principal's earlier revisions in the manifest, else
  `unknown_parent`.
- A reply that never parsed still counts as a revision.

**Submission order.** A reply has no sequence of its own. Order is numeric `createdAt` (exact nanoseconds; Senti
writes `isoformat()`, so the text does not sort), then the full action id, then the room id (`order_key`). The intake
persists its per-room `cursor` only after the reply it names is durably journalled.

## Validation

`validate_submission` (intake) and `validate_check_note` / `validate_check_request` (check) run these stages. Each
stage reports every violation it finds; the first stage with one ends the run, except that stages 5 and 6 report
together. At most 64 violations are listed, in canonical order; the outcome is decided before the list is cut.

| Stage | Codes |
|---|---|
| 0 chat | first non-blank bytes (after one optional BOM) neither `{` nor ` ``` `: `ignored` at intake, `malformed_json` at the check |
| 1 transport | `unattributable`, `edited_before_ingest` (intake only), `oversize` (over 4096 bytes), `not_utf8` (a BOM included) |
| 2 JSON | one object, bare or in one ` ```json ` fence: `too_deep` (a pre-scan, more than 4 levels), `malformed_json`, `duplicate_key`, `nonfinite_number` |
| 2s sealed | a `sentilab-open-sealed/1` envelope: its schema, `unknown_manifest`, `manifest_mismatch`, `sealed_key_version`, `sealed_format`; then the opener, `sealed_undecryptable`, and stages 1-6 on the plaintext, which needs `salt` (`salt_required`) and the envelope's manifest |
| 3 schema | `unknown_field` (path of the object), `schema_invalid` (path and keyword); a public proposal with a salt is `salt_forbidden` |
| 4 manifest | `unknown_manifest`, `manifest_mismatch` (`/manifest_id`, `/problem`, `/reference_id`, `/lattice_um`), `wire_track_not_admitted`, `terms_mismatch`; intake only: `manifest_closed`, `not_open_yet` (a draft is never open) |
| 5 geometry | `geometry_hash_mismatch`, `die_count`, `die_order`; then per die `rotation_not_allowed`, `out_of_frame`, `lattice` (exact integers) |
| 6 layout | the OP-F7 seam: `margin`, `halo_overlap`, `min_spacing` from `TapGeometry`, run only when every die maps onto its catalogue entry |

Outcomes: `ignored`, `rejected`, `refused` (a malformed check request: the error body), `sealed_unopened`,
`contract_valid` (no layout checker ran) and `legal`. Paths hold only schema-declared names and indices; nothing
submitted is ever echoed. Revision codes come from `decide_revision`; policy codes from the operational registry and budgets (OP-W1/W3).

**Seams.** `layout_checker(proposal, manifest)` returns stage-6 violations only; anything else raises. An
`opener(age_file, manifest)` returns the plaintext bytes or raises `Unopenable`; any other exception propagates.

## Limits

A note is at most 4096 bytes of strict UTF-8, nests at most 4 levels and has at most 32 dies. Coordinates are
integers in [0, 1,000,000] (the frame is checked per manifest); every string is a const, an enum or a pattern over a
charset without markup, quotes or controls; `client` is never rendered. Signed records fit the view envelope's caps.

## States

```
(reply) -> rejected                                                      terminal; codes; nothing charged
        -> queued <-> held
           queued -> evaluating -> evaluated -> reproducing -> reproduced -> verifying -> verified
                                -> failed                   -> not_reproduced           -> not_verified
           failed -> queued                                 operator requeue: a new attempt, both on record
           queued | held -> cancelled | expired             before any reservation; never charged
```

`reproduced` is a fresh-process replay on the pinned build; `verified` is the stronger cross-host or cross-build
result. `transition(entry, event, payload)` is pure. Guards: work starts only with a reservation id (`start`,
`reproduce`, `verify`); an attempt ends only when settled; `fail`, `not_reproduced` and `not_verified` need one code
of their group, `verified` a `cross_host` or `cross_build` tier, `reject` rejection codes only. Moderation events
(`hold`, `release`, `requeue`, `withdraw`, `restore`, `hide`, `unhide`) are operator-only. Two overlays sit on any
ingested state: `withdrawn` (restorable; no new work starts, in-flight work still settles; it shows publicly as
`withdrawn`) and `hidden` (`spam` or `not_a_layout`, undone with `reinstated`; hidden from public pages, never
deleted). The ticket's four states: rejected; queued (queued, held, evaluating); evaluated (evaluated, failed,
reproducing, reproduced, not_reproduced, verifying, not_verified); independently verified (verified only).

## Labels, claims and scoring

Every object that carries a measured temperature or wire value carries its `evaluator` identity (or `evaluators`,
when derived) and a `label`, which must be the SLAB-053 state of that identity: `withdrawn`, `unvalidated`,
`illustrative` or `accepted` (no identity is accepted yet). A derived value takes the most cautious state.

The challenge statistic `T_M_c` is the maximum native centre-map value across the real chiplets. The active-layer grid
peak and its argmax and the historical TAP selector are separate fields. Routed wire (judged) and the centre-distance
proxy (diagnostic) are separate fields. The comparator is the raw reference measured by the manifest's own evaluator
and router (`t_ref`, `w_ref`); paper targets are a separate, reference-only field.

Only a frozen manifest, with its reference measured, can be scored: comparisons, claims and controls are refused
otherwise. Uncertainty is a predeclared finite list of sensitivity cases, never a numeric bound. A claim:

- is decided (`passes_listed_cases` or `fails_listed_cases`) only from accepted or illustrative inputs; otherwise
  it stays `unknown`;
- is `incomplete` when a required case is missing;
- is `suppressed` when a required gate, binding, predicate or scenario failed, with the code in `suppressed_by`;
- never has a withdrawn input.

Strict (`W <= W_ref`), relaxed (`W <= factor x W_ref`, labelled RELAXED) and Pareto (`nondominated`) are separate claim
types. A control mismatch is a diagnostic result, and a row may also carry unexpected diagnostics with raw values.
A diagnostic has its own evaluator and label and never suppresses or replaces a claim or another value's label: a
high-wire diagnostic leaves the temperature's label as it is.

## Sealed proposals and checks

A manifest may publish an X25519 recipient for age v1 (`age-encryption.org/v1`), with a key version; a key rotates
only by a new manifest version. A sealed note is a `sentilab-open-sealed/1` envelope (manifest id, key version, format,
padded base64 of the binary age file) within the same 4096-byte note cap, with no plaintext fallback. Sealed entries
are never public: their receipt, status and results are served only to a `private-request` carrying their
`capability`.

The capability is a **bearer** capability: whoever holds it can read that submission's private status, results and
receipt. It is not authentication and proves nothing about authorship. It is a secret: never logged, never in any
record (restricted records keep `capability_sha256`, its `capability_epoch` and `capability_revoked`), and rotated to
the next epoch or revoked when exposed. The epoch is not secret; the salt is. **TODO:** no age implementation was available offline, so the
vectors hold no age ciphertext yet; generate them with age or rage before OP-F3 or OP-F7 relies on sealing.

## Accounting

`limits.provisional.json` keeps apart the request quotas, the evaluation quotas, the named call policy, the
check's solver limit and outer wall deadline (clock starts on admission; queue time excluded), and the CPU
reservation, enforcement and cleanup headroom. Each native call is one `usage` record under its suballocation; an
unmeasured call debits its full reservation. Live enforcement and overrun detection are separate fields with separate
states: `enforcement` says whether the process was stopped in flight at `enforced_cpu_s`; `overrun` says whether the
measured CPU exceeded the reservation, found at settlement. A detected overrun was not prevented; it only stops new
reservations. `no_participant_charge` holds only while the check is sponsored and both
time limits are set; it never means the sponsor spends no CPU. Every count binds to the account, whatever actor kind
posted.
