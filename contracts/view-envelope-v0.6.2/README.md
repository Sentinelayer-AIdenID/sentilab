# Live paging vectors (for DRAFT v0.6.2)

Paging vectors and a pure reference reducer for `VIEW-ENVELOPE.md` in this folder (sha256 a5a04e9c...), rules 4 and 5. v0.6.2 changes only rule 5:

- catching up is not progress;
- a finished run shows ENDED.

The merged v0.6 and v0.6.1 work stays unchanged in `../view-envelope-v0.6/` and `../view-envelope-v0.6.1/`. The envelope format and every verification rule are v0.5's. `paging.mjs` imports them from `../view-envelope-v0.5/view-envelope.mjs` and does not copy them. This is planning work, not a release.

## Files

- `paging.mjs` is the reducer and the reference server. It reads no clock, network, randomness or files, and it never mutates a state. The mode inputs (catch-up, highest K, last progress) live in the state.
- `vectors-paging.json` holds the vectors:
  - rule-5 label cases, testing each condition on its own through `liveLabel`;
  - bytes-to-rows cases;
  - cursor-hash cases;
  - server conformance for C7, C12 and C14;
  - scenarios C1 to C6 and C8 to C17, each with its polls, the run status at each poll, what the server does, hand-written expectations and the full trace. The trace records the label after every page.
  - C16's 273-envelope chain is generated by the rule in `chains`, and its rows' hash is recorded.
- `run-paging-vectors.mjs` regenerates every vector and checks it. It also checks invariants on every scenario and recomputes each hash separately. The V1 envelopes are read from `../view-envelope-v0.5/vectors-view.json`.

## Run

```
node run-paging-vectors.mjs           # check; exits non-zero on any failure
node run-paging-vectors.mjs --write   # rewrite vectors-paging.json from the code, then check
```

It was tested with Node 22.23 and has no dependencies.

## Exports

- **Client:** `initialState(runId, { limit })`, `request(state)` and `step(state, { status, headers, bodyBytes }, nowMs)`.
  - `request` returns `null` in a terminal state.
  - `step` returns `{ state, outcome, newRows }`, where `outcome` is `ok`, `transport`, `paging_error`, `stream_replaced`, `row_too_large` or `paging_unsupported`.
- **Progress:** `track(state, K, nowMs)`. Call it after each valid page with the K that `verifyRows` gives.
- **Verification:** `verifyRows(state, { pins, keys })` returns `{ verification, K, frozen }`. `verifyBytes(rows, options)` verifies raw rows, and `verifyReplayBytes(fileBytes, options)` does the same for a replay file.
- **Label:** `liveLabel(state, nowMs, K, frozen, runStatus)`, where `runStatus` is the run's status from `GET /api/view/runs` (`running` or `finished`).
- **Server:** `logRowsFromFile(fileBytes)` gives the complete rows of a log file. `servePage(completeRows, { cursor, limit, cursor_hash })` returns `{ status, headers, bodyBytes }`.
- **Byte helpers:** `cursorHash(rows)`, `splitRows`, `joinRows` and `rowText`.

## Rules as implemented

- **Bytes to rows.**
  - Raw bytes are split on LF (0x0A) only, and a trailing LF doesn't start a row.
  - Each row is decoded on its own as strict UTF-8, keeping any BOM.
  - A row that isn't valid UTF-8 is a `malformed` row with reason `invalid_utf8`. If it is over 64 KiB, it is `oversize` instead, because raw size is checked first.
  - A row that starts with a BOM is `malformed` with reason `not_json`.
  - The same rule applies to replay files, except that a replay file's last line may lack its LF and still counts as a row.
- **Cursor hash.** The cursor hash is SHA-256, lowercase hex, over the raw bytes of each row followed by one LF. Decoded text is never hashed.
- **A valid page** has status 200 and a body within 256 lines and 4 MiB. Its body, if not empty, ends with LF. Its `x-next-cursor` is a plain decimal equal to the cursor plus the rows returned. It holds no more rows than the requested limit. Its `x-cursor-hash` equals the client's own hash of every row it would then hold.
- **Failed polls.** A failed poll keeps no rows and never moves the cursor.
  - `transport` covers no response, a status other than 200, 400, 404, 409, 413 or 501, and a body over the caps.
  - `paging_error` covers a bad `x-next-cursor`, more rows than the requested limit, a non-empty body that doesn't end with LF, and a bad `x-cursor-hash`.
  - `stream_replaced` is a 409, `row_too_large` is a 413, and `paging_unsupported` is a 400, 404 or 501. All three are terminal: the client sends no more requests until a manual reload, which means a new `initialState`.
- **Progress.** Catching up is not progress.
  - Every valid page up to and including the first one with no more to fetch is history.
  - History rows raise the highest K but never count as growth.
  - After catch-up, K rising above its highest value is growth.
- **Label.** It is decided in this order:
  1. A finished run shows "ENDED · run finished", but integrity problems win. A terminal state keeps its label ("STALE · stream replaced", "STALE · row too large", "STALE · paging unsupported"), and then a frozen board shows "STALE · chain broken". A passing failure (transport, paging error) stays ENDED. A missing or unknown run status counts as running.
  2. For a running run, a failed latest poll shows "STALE · transport", "STALE · paging error", "STALE · stream replaced", "STALE · row too large" or "STALE · paging unsupported".
  3. Otherwise, if the board is frozen, the label is "STALE · chain broken", at once. The board is frozen when K is below the highest value it has reached, or when anything follows the projectable prefix.
  4. Otherwise v0.5's mode rule decides: LIVE needs a valid page within 5 s and growth within 60 s. The label reads "LIVE · progress N s ago", or "STALE".
- **Server.**
  - The log is its complete, LF-terminated rows. A tail with no LF yet is neither served, counted nor hashed.
  - A cursor or limit outside its range gets 400.
  - A cursor beyond the end gets 409, as does a cursor above 0 that comes without a `cursor_hash` or with one that doesn't match.
  - If the row at the cursor plus its LF is over 4 MiB, the answer is 413 with no body and no cursor headers.
  - Otherwise the page holds as many whole rows, each with its LF, as fit within 4 MiB, up to `limit`. It is never a 200 over 4 MiB.
