# 4. The engineering task and its judging mathematics

We will keep the current eight-chiplet thermal fixture as our initial domain.

The objective will be:

\[
J(x)=\max_{s\in S}\max_{i\in\{1,\ldots,8\}} T^{\text{center}}_{i,s}(x)
\]

Here:

- \(x\) is a proposed layout.
- \(S\) is the frozen set of power scenarios.
- \(T^{\text{center}}_{i,s}\) is the simulator’s center-mapped temperature for chiplet \(i\) in scenario \(s\).

**Lower is better, subject to the placement and interconnect constraints.**

Those constraints will include:

- Chiplets and required spacing remain within the interposer.
- Expanded footprints do not overlap.
- Coordinates follow the declared placement grid.
- The package, cooling assumptions and chiplet dimensions remain fixed for a task.
- A declared interconnect-distance budget prevents the agents from obtaining a trivial thermal improvement by spreading everything without limit.

For the first version, interconnect cost will be an explicitly labeled **weighted Manhattan-distance proxy** using the reference configuration’s connection matrix:

\[
W(x)=\sum_{i<j} c_{ij}
\left(|x_i-x_j|+|y_i-y_j|\right)
\]

We will set the permitted increase relative to each task’s starting layout before evaluation. This proxy is useful for the experiment; it is not a routed interposer or a timing signoff result.

## An important finding already in our work

The current simulator exports require careful interpretation. In the inspected configuration, the raw grid file represents the **substrate layer**, while the usable chiplet readings are center-mapped temperatures in the active chiplet layer.

Therefore:

- The initial objective uses the correctly identified chiplet-center readings.
- The display labels those readings accurately.
- An active-die peak-temperature objective would require a verified exporter and a new evaluator version.

This is exactly the kind of error our system should make visible and prevent from propagating into training data.

# 5. How we prove collaboration and learning

We need to separate two questions:

1. **Did sharing evidence help the collective?**
2. **Did changing the worker’s weights help?**

The experiment will include these conditions:

| Condition | Purpose |
|---|---|
| Conventional simulated annealing | Establish a non-LLM search baseline. |
| One lab with the base worker | Establish the single-lab baseline. |
| Four isolated labs with the base worker | Measure parallel search without information sharing. |
| Four communicating labs with the base worker | Measure the benefit of collaboration. |
| Four communicating labs with the adapted worker | Measure the additional effect of learned weights. |

The primary collaboration comparison is **four isolated versus four communicating**, using the same models and total budget.

The primary learning comparison is **base worker versus adapted worker**, with the other conditions held fixed.

### The budget contract

For the initial benchmark:

- Target **12 held-out task families**, with two paired evaluation seeds.
- Allow **32 total candidate-evaluation bundles per condition and task**, shared across the whole collective.
- Each bundle contains the required power scenarios.
- Reserve part of that budget for independent reproduction.
- Count failed evaluations and retries.
- Record model tokens, wall time and GPU time separately.
- Keep a fixed proposal ceiling so one condition cannot generate unlimited candidates for free.

The task families should group related power and placement variants before splitting. The conclusion will concern generalization within this declared benchmark domain.

The conventional baseline uses the same simulator budget. The agent conditions also have matched aggregate model budgets. If an API credit limit forces a smaller experiment, reduce it according to a rule established before seeing the final results.

### What the worker learns

Give the small worker a narrow, useful job:

> **Given a layout, constraints, previous evaluator feedback and a requested change, produce a valid structured engineering action or repair.**

That is a better weekend training target than asking it to become a complete chip designer.

Training records should contain:

- The task and evaluator versions.
- The input state.
- The proposed action.
- The actual validation error or measured result.
- The verified correction.
- A concise explanation of the correction.
- References to supporting tool outputs.

Store these as JSONL. Train primarily on our own structured state/action pairs and tool-verified corrections, with provenance for any additional examples.
