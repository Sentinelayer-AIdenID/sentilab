## Answers

- Default reconnection time: "must initially be an implementation-defined value, probably in the region of a few seconds" (lines 136-138). The spec gives no fixed number.
- `retry:` field: "If the field value consists of only ASCII digits, then interpret the field value as an integer in base ten, and set the event stream's reconnection time to that integer. Otherwise, ignore the field." (lines 418-420). The unit is milliseconds: the reconnection time is defined "in milliseconds" (line 136).
- Reconnect wait: "Wait a delay equal to the reconnection time of the event source." The UA may "wait some more", for example with exponential backoff (lines 283-287).
- `Last-Event-ID`: when reestablishing, if the last event ID string is not empty, the UA sets (`Last-Event-ID`, value encoded as UTF-8) in the request's header list (lines 293-297). The header "reports an EventSource object's last event ID string to the server when the user agent is to reestablish the connection" (lines 322-324).
- Non-200 or wrong Content-Type: "if res's status is not 200, or if res's `Content-Type` is not `text/event-stream`, then fail the connection" (lines 202-204). "Once the user agent has failed the connection, it does not attempt to reconnect." (lines 304-309). So yes: the client fails permanently (readyState CLOSED, `error` event) instead of reconnecting.
- In contrast, a network error (not an aborted one) leads to "reestablish the connection, unless the user agent knows that to be futile". A normal end of the response body also reestablishes (lines 196-204). The non-normative introduction says a client "can be told to stop reconnecting using the HTTP 204 No Content response code" (lines 93-94, in a section marked "This section is non-normative." at line 41). 204 is not 200, so it falls under the fail-the-connection rule above.
