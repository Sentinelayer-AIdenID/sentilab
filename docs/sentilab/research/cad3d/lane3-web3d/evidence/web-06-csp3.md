## Answers

- (a) worker-src fallback order: `worker-src` → `child-src` → `script-src` → `default-src` (S1, line 5728). worker-src "restricts the URLs which may be loaded as a Worker, SharedWorker, or ServiceWorker" (S1, line 4482).
- (b) `'self'`: blob is excluded explicitly. "If url's scheme is "blob", return "Does Not Match"." (S1, line 5167; S2, line 5181). There is no data:-specific line in the `'self'` branch. A `data:` URL's origin is "a new opaque origin" (S6, "Otherwise" branch), so it cannot be same origin with the page. It also has no host to match. So `'self'` does not match `data:`; this follows from the quoted text but is not stated as a single sentence. The `*` note says non-HTTP(S) schemes must be listed explicitly (S1, lines 5115-5118).
- (c) `'wasm-unsafe-eval'`: when a policy has `script-src` (or, failing that, `default-src`) without `'unsafe-eval'` or `'wasm-unsafe-eval'`, compilation is reported as a violation. With disposition "enforce" it is "Blocked", and `WebAssembly.CompileError` is thrown (S1, lines 2725-2765). The gated sinks are `new WebAssembly.Module()`, `WebAssembly.compile()`, `compileStreaming()`, `instantiate()` and `instantiateStreaming()`. `'wasm-unsafe-eval'` "only permits WebAssembly and does not affect JavaScript" (S1, lines 4015-4033).
- (d) CSSOM and style-src: UNVERIFIED as an explicit spec note. CSP3 has no note saying `element.style.x = ...` is or is not subject to style-src. What CSP3 does say: "The following CSS algorithms are gated on the unsafe-eval source expression: insert a CSS rule, parse a CSS rule, parse a CSS declaration block, parse a group of selectors". It adds "This would include, for example, all invocations of CSSOM's various cssText setters and insertRule methods". Then come an open issue ("This needs to be better explained", Issue #212) and an editor's placeholder ("I don't think CSSOM gives us any hooks here") (S1, lines 4232-4247 and 4320-4322). CSP2 (REC) has the same list, as a MUST throw SecurityError (S3). The specs do not settle per-property assignment. (i) The CSSOM camel-cased attribute setter (`el.style.fontSize = v`) "must invoke setProperty()", which parses a single value; that is not one of the four listed algorithms. (ii) CSSOM then writes the serialized declarations back to the `style` content attribute ("update style attribute for"). It sets an "updating flag" so that its own attribute-change steps return without re-parsing (S5). (iii) HTML says that when CSP blocks a style attribute, "the style rules defined in the attribute's value must not be applied" (S4). No quoted text says how (iii) interacts with the write-back in (ii), and CSP3 itself flags this area as "This needs to be better explained" (Issue #212). So: `cssText` setters and `insertRule` are explicitly gated (on 'unsafe-eval'). Per-property assignment such as `el.style.transform = ...` is not in the explicit list, but its CSP status is UNVERIFIED from the specs. Browser behaviour was not tested.
- (e) connect-src: "This directive controls requests which transmit or receive data from other origins. This includes APIs like fetch(), [XHR], [EVENTSOURCE], [BEACON], and a's ping. This directive also controls WebSocket [WEBSOCKETS] connections, though those aren't technically part of Fetch." (S1, lines 3343-3347). The example in the spec lists `new WebSocket(...)` and `new EventSource(...)` as blocked when they do not match.
